Definition

We run the .py file using the Python interpreter. Internally, CPython converts it into bytecode (.pyc) and executes the bytecode step by step. Python is a high-level, general-purpose language. C# .cs files are compiled first into a .NET assembly (.dll/.exe), then the CLR/JIT runs the IL.

Step-by-step (beginner friendly)

  • Step 1 — What is Python?
    Python is a language you write in text files ending in .py. You run them with the python command — no separate compile step like C#.
  • Step 2 — Interpreted, not machine code
    CPython reads your file, builds bytecode (.pyc), then executes that bytecode step by step. That is why we call Python interpreted.
  • Step 3 — Indentation = blocks
    Instead of { } braces, Python uses indentation (usually 4 spaces) after if, for, def.
  • Step 4 — Dynamic typing
    You do not write int x. A variable can hold a number, then a string — Python checks types at runtime.
  • Step 5 — Duck typing (real example)
    Key idea: A class having a method is normal. Duck typing is when another function uses that object without knowing the class name — only the behavior.

    1) Normal: you know the class and call its method.
    class EmailNotifier: def send(self, msg): return f"Email: {msg}" email = EmailNotifier() email.send("Order shipped") # you know it is EmailNotifier
    2) Duck typing: notify does not care about the class name — Email, SMS, or Slack all work if they have .send().
    class EmailNotifier: def send(self, msg): return f"Email: {msg}" class SmsNotifier: def send(self, msg): return f"SMS: {msg}" class SlackNotifier: def send(self, msg): return f"Slack: {msg}" def notify(channel, msg): return channel.send(msg) # no class name — only needs .send() notify(EmailNotifier(), "Hi") notify(SmsNotifier(), "Hi") notify(SlackNotifier(), "Hi")

    Remember: “If it walks like a duck and quacks like a duck, treat it as a duck.” In code: if it has .send(), call .send(). No shared base class / interface required. Same idea: save(writer, text) works with any object that has .write().

Interpreted vs compiled — step by step

  • C# path: .cs → compiler → IL (DLL) → JIT → native machine code → CPU runs it
  • Python path: .py → CPython compiles to bytecode → interpreter VM executes bytecode → result
  • Python feels instant because you run python file.py without a separate build step — bytecode is cached automatically in __pycache__/
  • Trade-off: generally slower than C#/C++ for CPU-heavy work; faster to write and test

Interview — questions & answers

Q: Is Python compiled or interpreted?

A: We run the .py file using the Python interpreter. Internally, CPython converts it into bytecode (.pyc) and executes the bytecode step by step. So Python is both compiled to bytecode and interpreted by the Python virtual machine.

Q: How is Python different from C#?

A: No mandatory type declarations, indentation instead of braces, and duck typing — if it has .send(), treat it as a notifier. C# usually requires an interface; Python checks behavior at runtime.

Q: What is duck typing — how is it different from a class that has a method?

A: A class having a method is normal OOP. Duck typing is when another function (like notify(channel, msg)) uses the object without knowing the class name — only that it has the needed behavior (.send()). Email, SMS, Slack all work with no shared base class. C# usually needs interface INotifier.

Q: Give a realistic duck typing example.

A: A notify(channel, msg) function that calls channel.send(msg). Email, SMS, or Slack classes all work if they implement send — no shared base class required.

Why immutable keys only? A dict uses hash(key) to place and find the value quickly (like a locker number). Mutable objects (list, dict, set) can change after you store them — then the hash would no longer match and the value would be lost or unreachable. Immutable keys (str, int, tuple, frozenset) never change, so the locker number stays valid.


List memory rule: Creating [] reserves a small buffer. Each append fills slots; when capacity is full, Python allocates a larger array and copies references — that is why sys.getsizeof jumps, not +1 every time.


Tuple vs list: Use tuple for fixed records (GPS, return pairs, cache keys). Use list when size changes (cart, rows, logs). Tuple is typically leaner/faster for fixed data because it never resizes.


Interview — questions & answers
Q: What is the difference between list and tuple?
A: List can append, slice, and change items — use for carts, rows, logs. Tuple is fixed — GPS, RGB, return ok, data, dict keys. Tuple usually uses less memory (no over-allocation) and is slightly faster for fixed-size data.
Q: How does list memory grow on append?
A: CPython over-allocates capacity. When the buffer is full, it allocates a larger array (~1.125×) and copies references. That is why sys.getsizeof jumps in steps instead of growing by one item each time.
Q: Can a list hold mixed types?
A: Yes. Homogeneous: [1, 2, 3] or ["a", "b"]. Heterogeneous: [101, "SHIPPED", ["Google", "Amazon"]] — int, str, and nested list together.
Q: Give real tuple use cases.
A: GPS (lat, lng), RGB color, employee record (id, name, salary), function return (ok, data), and composite dict keys like ("orders", 2026, 7).
Q: Why can't you use a list as a dict key?
A: Dicts locate values with hash(key) (like a locker number). A list can change after insert (append), so its hash would change and the value could not be found. Python raises TypeError: unhashable type: 'list'. Use a tuple instead: prices[(12.97, 80.22)].
Q: Why must dictionary keys be immutable?
A: Because the hash of the key must stay stable for the lifetime of the entry. Immutable types (str, int, tuple, frozenset) never change → safe. Mutable types (list, dict, set) can change → blocked.
Q: What types can be dictionary keys?
A: Immutable / hashable types: int, str, tuple, frozenset, bool, float. Not list, dict, or mutable set.
Q: What is the difference between set and frozenset?
A: set is mutable — add/remove items. frozenset is immutable like tuple. Use frozenset when you need a set as a dict key.

5except OSError:

8    log.info("ok")

1try


2{


3    Save(data);


4}


5catch (UnauthorizedAccessException)


6{


7    return 403;


8}

8

1class Product


2{


3    private decimal _price;

5    {

11}


Bottom line: Python @property ≈ C# property get/set. Descriptors are the lower-level mechanism behind @property.

C# Comparison — namedtuple vs record
Python namedtuple — lightweight record:


1from collections import namedtuple


2Point = namedtuple("Point", "x y")


3p = Point(10, 20)


4print(p.x, p.y)


C# record or readonly struct:


1public record Point(int X, int Y);


2var p = new Point(10, 20);


3Console.WriteLine(p.X);


Bottom line: namedtuple ≈ small immutable record. For APIs, prefer a Pydantic model or dataclass in modern Python.
